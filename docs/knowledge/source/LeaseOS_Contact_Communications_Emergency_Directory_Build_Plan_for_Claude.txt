1. Build objective and success criteria
Build one first-class LeaseOS contact service used by administration, dispatch, field drivers, safety, client portals, 
TDG/ERAP workflows, offline job packages and the AI Secretary. The subsystem is not a replacement for the device 
address book. It is an operational directory governed by organization, job assignment, role, contact-method classification 
and purpose.
 Company administration can maintain its workforce and operational directory: dispatch, safety, HR, payroll, 
mechanics, supervisors, managers, owner, drivers, labourers and other approved roles.
 Dispatch can assemble the exact contacts needed for a job, including client/consultant representatives, medic, 
disposal facility, site contacts, loading/unloading contacts, towing/recovery or other vendors.
 Drivers see contacts relevant to assigned work and approved historical relationships, not the entire corporate or 
client address book.
 Client users see only the assigned driver and explicitly published contractor contacts for that job, such as dispatch 
and designated emergency/safety contacts.
 Current-job emergency contacts remain available offline.
 Tapping a number hands the number to the device dialer; LeaseOS does not need to directly place calls in the initial 
implementation.
 Every sensitive read is authorized at the contact-method level and every important change is auditable.

2. Existing LeaseOS architecture alignment
This module should extend the existing LeaseOS design rather than create a parallel framework. The current project 
specification already establishes patterns that this module should reuse:
Existing LeaseOS rule How contacts must align
Tenant-scoped application data Every organization-owned contact, relationship, assignment and 
query is tenant-scoped unless it is an explicitly global LeaseOS-
managed emergency/system record.
Roles & permissions are an explicit missing admin layer Contact permissions should plug into the same role/permission 
service, not create a separate authorization system.
Append-only audit log Contact edits, publication changes, role/visibility changes, 
emergency catalog revisions and overrides produce append-only 
audit events.
Genuine offline architecture is planned Only authorized current/recent job contacts and emergency data 
are cached on the device; never mirror the entire organization 
directory.
Provenance is cross-cutting System-managed emergency contacts and imported/entered 
records carry source, status, verification date and accountable 
verifier.
AI proposes; humans commit important values The AI Secretary may locate/suggest contacts but may not 
silently publish private contact information or alter visibility.
Recommended integration point: implement the contact service after the shared role/permission foundation is available, 
then make dispatch, offline job packaging, emergency workflows and the AI Secretary consume it through a single 
service boundary.

Hard privacy boundary
Do not use READ_CONTACTS to bulk-ingest device contacts. Do not copy a worker's personal address book into 
LeaseOS. If a future feature lets a user add a LeaseOS work contact to their phone, make it an explicit one-contact 
export through the system contacts UI.
Authorization decision
authorizeContactMethod(actor, contactMethod, purpose, job?)
  1. authenticate actor
  2. establish tenant boundary
  3. load capability set
  4. check contact-method classification
  5. if job-scoped: verify actor/job relationship
  6. if client user: apply client projection allowlist
  7. if historical: verify prior assignment + history policy
  8. if emergency-only: verify emergency policy/purpose
  9. return ALLOW with redacted projection or DENY
 10. write audit/access event where policy requires
Fail closed. Unknown role, missing tenant, stale assignment, absent policy, deleted contact method or ambiguous scope 
returns DENY or a redacted record - never a permissive fallback.

8. Historical relationship catalog
Drivers need a catalog of approved contacts from jobs they personally worked, so repeat work with the same 
consultant/client/facility is easier. This is relationship history, not unrestricted directory search.
 Index by driver + organization + job participation.
 Show role, organization, last worked date, number of shared jobs and last verification date.
 Only return contact methods still active and permitted by the current classification/policy.
 If a method is stale or superseded, label it and prefer the current verified method if policy allows.
 Never allow history search to enumerate all members of a client/consulting company.
 Dispatch may use history as a suggestion source when creating a new job roster; a human confirms the assignment.

9. Emergency and ERAP directory
Emergency data needs stronger provenance and availability than ordinary contacts. Model two sources: (1) 
LeaseOS/system-managed official emergency records and (2) tenant/job-supplied emergency contacts. Keep source, 
jurisdiction/scope, verification date and status on every record.
ERAP behavior
 Do not treat an ERAP telephone number as a universal catalog constant.
 When a shipment requires an ERAP, bind the ERAP reference number and ERAP telephone number from the 
applicable shipping document/manifest to the job/load emergency roster.
 Preserve sourceDocumentId and the exact effective value used for the trip/job.
 If the manifest changes, create a new binding/revision rather than silently overwriting the prior value.
 Only surface an ERAP number for the load/manifest to which it applies.
System emergency seed records
At minimum, seed 911 for local emergency calling and the current Transport Canada CANUTEC numbers as system-
managed records, with source metadata and a scheduled verification process. As of this build-plan date, Transport 
Canada lists 1-888-CAN-UTEC (226-8832), 613-996-6666 and *666 on a cellular phone in Canada for dangerous-goods 
incidents. Keep these values configurable and source-verified rather than permanently hard-coded in application logic.
Emergency UX rule
Emergency access must be simple, highly visible and offline-capable, but emergency visibility does not erase 
tenant/job privacy boundaries for unrelated personal numbers.
10. Mobile call handoff and device permissions
For Android, the preferred initial behavior is to hand the selected number to the system dialer. Use ACTION_DIAL with a 
tel: URI. The dialer displays the number and the user confirms the call. Do not use ACTION_CALL unless a future, 
separately justified requirement needs direct calling.

11. Offline-first behavior
This subsystem must integrate with LeaseOS's genuine offline plan. The contact cache is a projection, not a database 
replica.
Cache on device Do not cache broadly
Current assigned-job contacts Entire company directory
Current-job client/consultant/medic/disposal contacts Unrelated client organizations
Required company dispatch/safety contacts HR/payroll/private employee records
Current-job ERAP binding and approved emergency directory Historical contacts the user is no longer authorized to access
Limited recent relationship history if enabled by policy All partner/vendor records
 Encrypt local contact data using the same secure local-storage strategy as other LeaseOS offline records.
 Include authorization version / assignment fingerprint in cached packages.
 On reconnect, invalidate removed assignments and stale contact methods promptly.
 Do not silently merge conflicts in visibility/classification. Surface them to an authorized human.
 Offline emergency view must clearly show last-sync/verification timestamps where relevant.

13. AI Secretary integration
The AI Secretary must consume the same contact service as every other client. Do not grant the model raw-table or 
cross-tenant directory access.
 Provide typed tools such as findJobContact(jobId, role), findDisposalContact(jobId), findCompanyDispatch(), 
findEmergencyContact(jobId, type).
 The tool layer enforces actor identity and authorization before returning fields to the model.
 The AI can suggest adding a known historical contact to a job, but dispatch/human confirmation is required to 
publish it.
 The AI may say that a contact is unavailable or restricted; it must not infer or fabricate a number.
 When asked to call, the AI should resolve the authorized target and open the dialer - not place the call silently.
 Agent prompts/logs should avoid retaining private_personal values unless absolutely required for the specific 
authorized task.

16. Staged implementation plan
Build in vertical slices. Each phase must leave the repository green. Do not build all UI first or all schemas first without 
proving the authorization path end-to-end.
Phase C0 - Repository reconnaissance and contract freeze
Inspect current schema, routers, auth middleware, tenant context, jobs, users, facilities, offline work and auditLog 
implementation. Identify existing person/user/org concepts before adding tables. Write a short mapping of reused vs new 
entities. No parallel auth or tenant system.
Phase C1 - Contact domain + authorization foundation
Add/extend people, organization memberships, contact methods, classification enum and contact service. Implement 
field-level authorization. Add migrations, indexes, tenant constraints and unit tests for every classification.
Phase C2 - Company directory vertical slice
Admin creates a worker work-phone contact; dispatcher can retrieve it if permitted; driver cannot retrieve 
restricted/private method. Add UI for internal directory and verification/status.
Phase C3 - Job contact roster + client projection

17. Testing and release gates
Mandatory automated test families
 Tenant isolation: tenant A cannot discover tenant B people, methods, relationships, history or job rosters by ID 
guessing, search, pagination, export or AI tool.
 Classification matrix: every role/capability against every classification for read, dial, publish and edit.
 Job assignment: assigned vs unassigned driver, active vs completed vs cancelled job, client vs internal projections.
 Historical relationship: prior participant allowed only within configured policy; unrelated coworkers denied.
 Client projection: never returns HR, payroll, unrelated mechanics/drivers, internal-only methods or other clients.
 Emergency: current job ERAP appears only when bound/applicable; revision preserves old binding; offline package 
contains required emergency set.
 Mobile privacy: no READ_CONTACTS dependency; ACTION_DIAL path; denied/redacted numbers never appear in 
intents/logs.
 Offline: revoked assignment invalidates cached access; stale data visibly marked; no automatic visibility conflict 
merge.
 Audit: important create/update/supersede/publish/assignment events are append-only and attributable.
 AI tools: no raw directory enumeration, cross-tenant leakage, hidden-field leakage or fabrication when contact is 
unavailable.
Release gate
Gate must be green
Company admin creates a work contact -> dispatch assigns it to a job -> assigned driver sees only allowed methods 
-> client sees only published subset -> driver taps Dial and system dialer opens -> offline job package preserves 
authorized emergency/job contacts -> assignment is revoked and access disappears -> audit history remains intact.

18. Migration and rollout
1. Inventory existing user/driver/client/facility phone/email fields and classify each source before migration.
2. Create canonical contact methods without deleting legacy fields immediately.
3. Dual-read during a short compatibility period if necessary; new writes go through the contact service only.
4. Migrate company work contacts first. Do not automatically promote arbitrary legacy personal numbers to 
operational/client-visible classifications.
5. Require admin review for ambiguous employee numbers and all client-visible defaults.
6. Migrate facilities/disposal contacts with organization ownership and source/verification metadata.
7. Enable job rosters for a pilot tenant, then emergency/offline/history in controlled phases.
8. After parity and audit checks pass, remove deprecated direct phone/email reads from old modules.
9. Add a structural test that fails if protected contact tables are queried outside the approved repository/service 
boundary.
