Repository hygiene, done before C1 and A3. No production code, schema, migration or API change.

## Root cause

`LEASEOS_CURRENT_STATE.md` is generated by `scripts/current-state.sh`, and gate 8 fails if the
committed copy differs from a fresh run. One row was `Test files / cases | **486 / 6642**`.

The file's history shows where the churn came from. Of the 105 non-merge commits that changed the
document:

| Row | Commits that changed it |
|---|---|
| **Test files / cases** | **105** |
| Migrations | 27 |
| Role-authorized procedures | 24 |
| Tables | 18 |
| Sensitive permissions | 17 |
| Permissions | 15 |
| Universal permissions, Release | 7 each |
| Portal procedures, native bindings | 2 each |
| Bare `protectedProcedure`, integration procedures | 1 each |

**69 of the 105 changed nothing but the test row.**

Almost every pull request adds a test. So every open branch regenerates the same line to a
different number, and git conflicts whenever two branches write different values into it. Merging
any one branch into main therefore put every other branch that added tests into conflict. PR #105
had to be re-synced three times in one morning for this line alone. Picking either side is wrong:
the merged tree's count is neither parent's (`scripts/reconcile-main.sh` explains this). So every
conflict cost a merge, a regeneration and a fresh CI run.

## Classification

**Architecture-state metrics: stay committed and checked.** These are release, tables, migrations,
role/portal/integration procedure counts, bare `protectedProcedure` (must be 0), permissions,
sensitive and universal permissions, and native-only runtime bindings. They move when the
architecture moves. A pull request that changes one should say so in the document everyone reads,
and the gate still fails if it doesn't.

**High-churn build metrics: computed by the gate, not committed.** These are test files and test
cases. The prose sections of the document are hand-maintained claims checked by
`documentationTruth.test.ts`, and they are unchanged.

## Design

- **Document.** The `Test files / cases` row stays but carries no number. It reads
  `computed by the gate, not committed` and names the command and the artifact.
- **`scripts/current-state.sh --metrics [PATH]`** writes
  `artifacts/current-state-metrics.json` by default. It uses the same runner-backed file list
  (`vitest list --filesOnly`, which refuses an empty answer) and the same `it(` arithmetic as the
  old row.
- **Determinism.** The JSON has three keys in a fixed order, and no timestamp or host, so two runs
  over the same tree are byte-identical.
- **Gate 8** still regenerates the whole document and fails on any difference. It then runs
  `--metrics`, prints the JSON, and appends it to `$GITHUB_STEP_SUMMARY` when present. That makes
  the totals visible on every CI run without changing the workflow file, which
  `check-version-truth.mjs` guards.
- **`/artifacts/` is gitignored**, so the totals cannot drift back into a commit under another
  file name.

The new test file accounts for the difference from main's 486 / 6642: +1 file, +9 cases.

## What still fails the gate

- Any architecture count in the document differing from the tree: tables, migrations, procedures,
  permissions, native bindings, release. Test C proves this with one more `mysqlTable(`. The
  regenerated document differs in the Tables row and nowhere else.
- Any change to the generated prose without regenerating.
- A runner that lists no tests. `--metrics` fails closed, exits non-zero and writes nothing, and
  gate 8 fails with it.
- All of `documentationTruth.test.ts`, unchanged.

## Tests — `server/currentStateMetrics.test.ts`

| Case | Proves |
|---|---|
| A ×3 | Adding a test (+1 file, +3 cases, in a temp dir, substituted through `LEASEOS_VITEST_LIST_CMD`) moves the metrics by exactly that. The document generated with and without it is byte-identical *and* equal to the committed one. The row and the template carry no total. |

the JSON fails D.

## Conflict proof

I ran two scratch branches from each base. Each added a different test file (A: 1 case, B: 2
cases), then I regenerated the document on each and merged A into B. Nothing was pushed, and the
worktrees and branches were removed.

| Base | A's document | B's document | Merge |
|---|---|---|---|
| main `85fdc13` (before) | changed, `487 / 6643` | changed, `487 / 6644` | **CONFLICT in LEASEOS_CURRENT_STATE.md** |
| this branch (after) | unchanged | unchanged | **clean** |

When both branches add the same number of cases, the before case merges cleanly, because git
accepts identical changes on both sides. That is why the conflicts looked intermittent. Real
branches rarely add the same number.
