# ELD Checkpoint 1a — protocol hardening: an implementation-independent canonical form

**Branch:** `claude/eld-compliance-intelligence-ramlrd`. **Base of this checkpoint:** `5bf73cb` (Checkpoint 1).
**Scope:** the hashing/canonicalization protocol, its golden vectors, the declared-hash check, the chain
vocabulary, the conflict-evidence semantics, and the migration number. No HOS mechanics, no dispatch,
readiness, diagnostics tables, compliance findings, dashboards or UI.

## 1. How `eld-h1` produced its bytes before this checkpoint

`canonicalEldEventJson` built a JavaScript object with 21 keys in declaration order and returned
`JSON.stringify(obj)`; `payloadHash` was SHA-256 over that string's UTF-8; `eventHash` was SHA-256 over
`"eld-h1\n" + (previousEventHash ?? "") + "\n" + payloadHash`. Every byte therefore depended on the
ECMAScript runtime:

- **Numbers** — `latitude`, `longitude`, `locationAccuracyM`, `odometerKm`, `engineHours`,
  `vehicleSpeedKph` were IEEE doubles printed by `Number::toString`: shortest round-trip digits,
  `1e+21` and `1e-7` exponent forms, `0.1 + 0.2` → `0.30000000000000004`. No stated precision.
- **Timestamps** — `eventAt` was accepted as any ISO-8601 text and re-emitted through
  `Date.prototype.toISOString()` (`2026-09-11T14:00:00.000Z`).
- **Strings** — ES `JSON.stringify` escaping (the seven short escapes, `\u00xx` lowercase for other
  controls, raw non-ASCII, and lone surrogates silently escaped as `\udXXX`).
- **Key order** — object insertion order, i.e. the order of a TypeScript object literal.
- **Identity fields** — `unitId`, a database-generated id.

A non-JavaScript producer would have had to reproduce all of that. The batch *signature* already used a
sorted-key canonical form (`canonicalDevicePackage`) and was not the problem.

## 2. The canonical form now

Specified in full in `shared/eld/eldEvent.ts` and restated in `ELD_CANONICAL_FORM.md`: UTF-8, no BOM;
objects with keys sorted by code point; arrays in order; strings with exactly the JSON short escapes plus
lowercase `\u00xx` for other controls and everything else raw; integers only (`-?(0|[1-9][0-9]*)`,
≤ 2^53 − 1); no whitespace; absence = null; timestamps as integer milliseconds; UUIDs lowercase; hashes
lowercase hex. A strict subset of RFC 8785, implementable in ~60 lines with no library. Option B from the
brief (a small LeaseOS-defined encoding with explicit rules) was chosen over adopting a JCS dependency:
the rules are the same where they overlap, and stating them removes the dependency risk.

Fixed-scale integers replace floats: `latitudeE7`, `longitudeE7`, `locationAccuracyMm`, `odometerM`,
`engineHoursMillis`, `vehicleSpeedKphMillis`. The precision is now explicit (10^-7 °, 1 mm, 1 m,
0.001 h, 0.001 km/h) where before it was undefined; the derived `double` columns are unchanged and are
computed from the integers by the store. `eventAt` became `eventAtMs`. `unitId` became `unitNumber`.

## 3. Hash version decision: `eld-h1` corrected in place

Checked, not assumed: `5bf73cb` is contained only in `origin/claude/eld-compliance-intelligence-ramlrd`;
no tag contains it; `origin/main` has no `shared/eld`, no `eldEvents` table and no ELD migration;
`LEASEOS_RELEASE` on main is v23.25. The string `eld-h1` appears nowhere outside this branch. Every
`eldEvents` row ever written existed only in disposable gate databases. There is no persisted or
production-compatible data that could depend on the old bytes, so carrying a known-bad definition under a
new version number would have preserved nothing and cost a permanent verification branch. `eld-h1` is
redefined; no `eld-h2` exists. The `hashVersion` column stays so a future change can be versioned.

## 4. Golden vectors

`shared/eld/vectors/eld-h1.vectors.json`: 19 event vectors and 8 value vectors, every canonical text and
SHA-256 a literal. Generated by `shared/eld/vectors/eld_h1_reference.py`, which shares no code with the
TypeScript encoder and rests on Python's standard `json` module (`sort_keys`, compact separators,
`ensure_ascii=False`) — a genuinely independent implementation of rules 1–6. `server/_core/eldCanonicalVectors.test.ts`
pins every vector through both `canonicalEldEventJson`/`hashEldEvent` and the production batch path.
Cases: minimal; complete; explicit nulls equal absence; empty string; Unicode (accented, BMP symbol,
astral); quotation mark; backslash; control characters incl. DEL; U+2028/U+2029 raw; negative and
positive coordinates; coordinate bounds; timestamp and range edges; predecessor hash; correction;
uppercase UUID normalization; 2^53 − 1; another device; nested unsorted object; arrays; empty containers;
key ordering; literals; integers; every escape; empty string.

## 5. Field participation audit

| Category | Fields |
|---|---|
| device-authored, hash-participating, required | `eventRef`, `deviceSequence`, `eventType`, `recordOrigin`, `eventAtMs` |
| device-authored, hash-participating, optional (null when unset) | `eventCode`, `dutyStatus`, `eventUtcOffsetMinutes`, `latitudeE7`, `longitudeE7`, `locationAccuracyMm`, `locationSource`, `jurisdiction`, `odometerM`, `engineHoursMillis`, `vehicleSpeedKphMillis`, `annotation`, `supersedesEventRef` |
| resolved server identity through a stable device-visible identifier | `deviceRef` (minted at enrolment, held by the device, checked against `fieldDevices`); `unitNumber` (resolved to `units.id` and checked against ownership) |
| protocol constant | `hashVersion` |
| server-authored, excluded (unavailable at device creation time) | `id`, `orgRef`, `operatorId`, `unitId`, `receivedAt`, `sourceKind`, `sourceRef`, `submittedByUserId`, `createdAt` |

The hash proves the integrity of what the device claimed. Who owns the event is the server's separate
determination: tenant from `fieldDevices.orgRef`, operator from the device's user, unit from ownership.
No identifier in the hash material makes a client's tenancy claim trusted, because none is read as one.

## 6. Declared hash

The server always canonicalizes and hashes what it received. `declaredEventHash`, when present, is
compared to that result and the batch is refused on a difference; it is never used in place of the
computation. Tests: a correct declaration is accepted; a well-formed wrong hash is refused; the *true*
hash of different content, declared for altered content, is refused (pure and database-backed); an event
without a declaration hashes identically.

## 7. Sequence continuity and hash continuity

Two questions, answered separately by the pure `assessDeviceChain`: gaps (sequence) and, per event, a
link state — `first`, `linked`, `predecessor_missing`, `hash_mismatch`, `missing_claim`,
`dangling_first` — plus ordering inconsistencies (a later sequence with an earlier device clock). An
out-of-order event is stored; its link is `predecessor_missing` until the predecessor arrives, then
`linked` or `hash_mismatch`, with no row rewritten. No diagnostic table exists.

## 8. Conflict evidence semantics

`UNIQUE(canonicalEventId, attemptedEventHash)` is deliberate. `eldEventIngestConflicts` is **content
evidence**: the first conflicting payload for a canonical row is preserved whole; an exact repeat of the
same conflicting payload is idempotent (same `conflictRef`, no second row); a different conflicting
payload is different evidence and gets its own row. It is **not an attempt-frequency counter**: the rows
are immutable (triggers), carry no `attemptCount` or `lastSeenAt`, and never will. Frequency belongs in a
later ingest-observation stream (`FOLLOWUPS.md` F-6). Tested: three identical conflicting deliveries →
one row, one ref; a second distinct conflict → a second row; the canonical row byte-identical throughout.

## 9. `eldEvents.fieldDeviceId` is nullable

Today's store writes only enrolled LeaseOS field devices and always sets it (asserted in the database
suite). The column is nullable for the boundary in `FOLLOWUPS.md` F-5: a third-party ELD is a *source
device identity* (a provider's device id under an `integrationClients` row, or a hardware serial), not a
`fieldDevices` row and not "no device". The intended shape is an `eldSourceDevices` table that
`eldEvents` points at, with `fieldDeviceId` remaining the LeaseOS-app case. No schema change now.
